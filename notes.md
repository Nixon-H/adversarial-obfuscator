## Research-harness audit (current HEAD)
- User-facing product documents two separate paths: scripts/build.py native builder and python -m obfuscator.core.pipeline hybrid loader (README.md). scripts/transfer/experiment.py evaluates scripts/diversity.generator and ObfuscationTransformer, not the complete default production build. Scope paper claims accordingly.
- H0-H5 runner always calls gen.generate(..., 1, td) (scripts/transfer/experiment.py:57-64); generator chooses pass_sets[variant_id % len(pass_sets)] (scripts/diversity/generator.py:30-45). Every call has variant_id 0. Therefore H1 and H5 never rotate through their configured pass sets. H0 and H1 have the same first set/options; H5 adds rep_diversify and alternating vm_dispatch to that same first set. The purported heterogeneous selection treatment is not tested.
- Generator hardcodes strip_meta, unfold_constants, obf_calls true (scripts/diversity/generator.py:47-62). H0/H1/H5 leave them true; H2/H3/H4 use ISOLATION_OFF (scripts/transfer/arms.py:9-29,31-72). Therefore cross-arm comparisons are confounded by these transformations.
- measure.taxonomy_transfer() filters hetero:/seed_only: keys (scripts/transfer/measure.py:68-76) while saved experiment keys are H0-H5. Data introspection confirmed all six docs/research/h0h5-results/*/experiment.json files contain 1,296 endpoint entries but zero grouped T_hetero and T_seed values. docs/research/protocol-v2.md says this was fixed; checked-out code/results disagree.
- S_cfg means vector-confirmed function mapping, not CFG recovery (scripts/transfer/measure.py:80-105). S_cfg_boundary is candidate-map presence. Constant extraction in static arm is source substring search (scripts/transfer/attack.py:289-295).
- Static attack develops using original source AST features and known vectors (scripts/transfer/attack.py:210-238), then applies frozen clean-source features to per-target AST features and uses target vectors (:262-288). The learned artifact does not carry a target-specific reverse-engineering result; marker counts are extracted but not used by apply(). Label this known-source/oracle-assisted template matcher, not a general RE attacker.
- H0-H5 inference compares 36 ordered within-arm build-pair cells, includes six self-pairs fixed at T=1, and reuses the same six builds across cells (scripts/transfer/experiment.py:155-167). bootstrap_ci resamples pair values although module prose says function-level bootstrap (scripts/transfer/measure.py:18-20,144-158). Use cluster-aware inference at build/project level and exclude self-pairs from cross-transfer inference.
- Diversity proxies are mislabeled/weak: _cfg_blocks_and_edges counts AST control constructs, not CFG edges (scripts/diversity/metrics.py:39-56); compute_bytecode_similarity n-grams raw .py file bytes (:120-145); compute_ir_similarity counts AST features. These do not independently validate the reported structural-diversity/transfer relationship.
- VM result is limited to a stale-map decoding experiment on calc, the only VM-eligible program. Extractor parses emitted VM tables from target AST; aligner uses exact true-op sequence as evaluator scaffolding (scripts/transfer/vm_attack.py:286-327,330-376). Result supports “a frozen opcode map fails after random permutation”; it does not support “a target-build attacker cannot extract the new map.” docs/research/vm-transfer.md points its raw 18x18 matrix to /tmp/opencode/vm_matrix.json, which is not versioned in the repo.
- Corpus consists of six hand-written 37-51 LOC programs, 3-4 functions/program, and 4-8 total vectors/program (scripts/transfer/corpus/*/*). This is useful for a pilot, too small/narrow for claims about broad Python packages.
- Const-split v2 is better scoped, with 72/72 build semantic gates and a pre-measurement amendment, but has 3 builds/arm/program and measures literal search in CPython co_consts, not algebraic/value recovery (docs/research/protocol-v2.md; docs/research/const-split-results/RESULTS.md).
- Ghidra pilot was rejected for a binary-size/function-count confound (docs/research/ghidra-pilot.md); no robust independent decompiler/LLM/symbolic attack currently anchors broad resilience claims.
- Planner is scaffolding, not empirical adaptive planning: scripts/synthesis/costs.py manually assigns gains and overheads; it is not fitted to measured success/cost, and the problem definition assumes additive benefits (scripts/synthesis/engine.py, scripts/synthesis/optimizer.py).
- Good research assets: freeze hashes and protocol docs, transparent recording of failed instruments/repairs, raw H0-H5 artifacts, explicit limits in threat model, and no use of “unbreakable.” Engineering CI and regression tests do not themselves establish research efficacy.

## Literature screen (rapid, not systematic)
- Direct precedent makes broad novelty claims unsafe: CoDiver randomizes VM opcode/semantics mappings across partitions to block re-use of analysis knowledge ([IEEE Access 2019, DOI 10.1109/ACCESS.2019.2954165](https://doi.org/10.1109/ACCESS.2019.2954165)); DCVP partitions virtualized regions and remaps opcodes to handlers ([ICPADS 2018, DOI 10.1109/PADSW.2018.8644535](https://doi.org/10.1109/PADSW.2018.8644535)); N-Version Obfuscation addresses replicated tampering through program diversity ([ACM CPSS 2016, DOI 10.1145/2899015.2899026](https://doi.org/10.1145/2899015.2899026)).
- Python obfuscation empirical work already exists: the EASE 2025 paper studies LLM-driven obfuscation on Python functions and semantic correctness ([EASE 2025](https://doi.org/10.1145/3756681.3757041)); this is adjacent, not itself a cross-build attack benchmark.
- Existing measurement work includes a source-code obfuscation framework based on CFG, paths, and performance ([Applied Sciences 2024, DOI 10.3390/app14125056](https://doi.org/10.3390/app14125056)) and a 2026 human study of obfuscation's effect on attacker effort and whether complexity metrics predict outcomes ([Computers & Security, DOI 10.1016/j.cose.2026.104881](https://doi.org/10.1016/j.cose.2026.104881)).
- De Sutter et al. reviewed 571 software-protection papers and identify methodology/reproducibility issues ([ACM Computing Surveys 2024, DOI 10.1145/3702314](https://doi.org/10.1145/3702314)); this supports a rigorous protocol, not an automatic novelty claim.
- Deterministic seeded obfuscation is existing engineering practice, e.g. [Obfuscator-LLVM FAQ](https://github.com/obfuscator-llvm/obfuscator/wiki/FAQ) and current [xollvm seed documentation](https://xollvm.github.io/concepts/determinism/). Pinning entropy improves reproducibility, but is not on its own a novel security contribution.
- The strongest candidate is a carefully validated benchmark/study distinguishing (1) frozen transfer of a specific analysis artifact and (2) adaptive target-specific recovery/adaptation cost for Python builds. Whether that exact benchmark contribution is novel remains unverified: this is a rapid screen, not a systematic review.

## Candidate paper plan
- Working question: Under which attacker capabilities does analysis learned from one diversified Python artifact transfer to another, after accounting for target-specific adaptation, correctness, and overhead?
- Candidate title: “When Does Analysis Transfer Across Obfuscated Python Builds? Measuring Frozen and Adaptive Attack Reuse.”
- Main contribution should be a precise benchmark/protocol and evidence about a specific attack-transform pairing, not “new obfuscator is secure.” Keep product-security claims separate from software-only MATE limits.
- Minimum order: (1) new versioned protocol; fix arm-selection and taxonomy bugs; rename endpoints; (2) isolate arms and define whether clean source/test vectors are attacker knowledge or evaluator-only; (3) replace diversity proxies with actual AST/bytecode/CFG metrics and validate them; (4) compare frozen artifact reuse to adaptive target extraction using realistic attack tools; (5) use a diverse open-source Python-project corpus with more functions and stronger differential/property tests; (6) preregister endpoints, power, exclusions, multi-comparison policy and cluster-aware analysis; (7) reproduce on a clean machine and publish raw artifacts/commands/environment.
- No implementation or test changes were made in this audit; no test suite was run. Only research-data JSON introspection and read-only source review were used.
