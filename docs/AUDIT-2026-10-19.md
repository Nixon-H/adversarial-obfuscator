## 1. Executive Summary

The repository is in materially better shape than the session's own reports
claimed, because the fixes from 2026-09-27 → 2026-09-29 landed after the
audit. Re-verification against `f76325d` shows most of the four final-round
agent findings are already closed.

Three findings were **not** in the agent reports and are new here. All three
were found by doing what the agents were asked to do but did not do — tracing
the *shipped artifact* rather than the module internals:

1. **The default build produced a dead artifact ~80 % of the time.** The
   adversarial prompt-injection pass runs *after* the string obfuscator and
   rewrote the emitted ChaCha20 seal literals. The stub raises
   `ValueError("bad string seal")` on a malformed seal, so the artifact died
   at import. Fixed; 25/25 consecutive builds now run.
2. **The same pass injected a numpy training loop into the ChaCha20
   rotate-left helper**, which made the remaining builds appear to hang.
   Fixed with the same change.
3. **`mlockall(MCL_FUTURE)` leaked out of `MemoryGuard`**, permanently capping
   every later page fault at `RLIMIT_MEMLOCK` (8 MB on this host). This is a
   production bug, not only a test bug: the second monitored call through
   `KernelAssistedExecutor` leaves the process unable to allocate. Fixed.

The repo's own `test_opcount_truth.py::test_no_bare_141_claim_in_code` was
**failing at `f76325d`** (a generated research artifact contains the digits
"141" by coincidence, not as a verified op-count claim). Fixed.

After these fixes the whole test suite is green: **4098 passed, 14 skipped,
0 failed** (main suite 5 m 01 s, bench group 2 m 38 s), and 25/25
consecutive default builds produce an artifact that actually runs.

One structural caveat applies to every performance/robustness number in the
repo: the host used for this audit was under memory pressure (≈230 MB free
of 7.6 GB, with the agent session's own tooling accounting for 6.3 GB of
RSS), so the full suite had to be run in slices. That pressure is also what
turned the `mlockall` leak (§3.2) into a visible z3 segfault; the leak
itself is host-independent. The measured results are in §15.3.

## 3. High-Severity Issues

### 3.1 Adversarial injection corrupted the emitted seal and decoder stub — FIXED

| Field | Value |
|---|---|
| Severity | **HIGH** (default build produced a non-running artifact) |
| Files | `obfuscator/adversarial.py:223-303` (`_inject_prompt_strings`), `obfuscator/adversarial.py:178-217` (`_inject_func_dead_code`) |
| Found by | end-to-end build→run loop (not present in the five agent reports) |
| Affects v19 | yes — it is the default build path |
| Regression | introduced by `bc6b527` (2026-09-29, "ChaCha20 string default"); latent before, silent in XOR mode |
| Safe to fix | yes, fixed here |

**What.** `scripts/build.py` Stage 1.5 runs
`phase_adversarial_injection` on the *already-obfuscated* payload
(`config/default.json` sets `phase2.enabled=true` and
`phase2.features.adversarial=true`, so this runs by default). The pass
prefixes a prompt string to arbitrary string literals:

```python
node.value = prompts[injected] + " | " + node.value   # adversarial.py:249
```

After the string obfuscator, almost every literal in the file **is** a
ChaCha20 seal (`<var> = '<seal hex>'`). Prefixing prose to one of them
corrupts it, and the emitted stub fails closed:

```
File "build/hello_obfuscated.py", line 20, in _nixon_…
    _nx_r = bytes.fromhex(_s)
ValueError: bad string seal
```

**Why it is a problem.** The measured failure rate matched the model exactly:
with ~10 seals per artifact and a 15 % per-literal injection probability,
`1 - 0.85^10 ≈ 80 %`. Measured at `f76325d`: **1 build in 5 ran, 4 died.**
The README quick-start — the first thing a new user runs — was broken.

A second failure mode came from the same pass: `_inject_func_dead_code`
injected the numpy training-loop template into the ChaCha20 rotate-left
helper nested inside the decoder stub, so *every* seal decryption ran a
15-iteration numpy loop. The artifact did not error — it simply took
effectively forever (confirmed with `timeout -s INT`, which showed the
stack inside `_nx_rl`).

**Fix.** Two guards in `obfuscator/adversarial.py`:

* `_is_seal_literal()` recognises an emitted seal (hex, even length, ≥ 28
  bytes) or a legacy XOR seal (base64) and the prompt pass never rewrites
  one. A false positive only means a prompt is *not* injected — it can
  never break the artifact.
* `_protected_function_ids()` protects the whole subtree of the emitted
  decoder stub (detected by its `_s` parameter and `fromhex` body) from
  both the dead-code and the prompt passes.

When no safe literal exists to carry a prompt, `_inject_prompt_constants()`
lands it as a standalone plaintext module constant instead — the pass runs
after the obfuscator, so the prompt stays readable in the artifact, which is
the whole point of the feature.

**Verification.** 25/25 consecutive default builds now produce an artifact
that prints `hello-nixon`; 12/12 in a second independent run. Prompts are
still present in the artifact as plaintext (`_nx_prompt_0`, `_nx_prompt_1`),
and no seal literal is modified. Regression tests:
`tests/test_adversarial_seal_integrity.py` (4 tests, including an
end-to-end build→run loop over 5 builds).

### 3.2 `mlockall(MCL_FUTURE)` leaked out of `MemoryGuard` — FIXED

| Field | Value |
|---|---|
| Severity | **HIGH** (production bug: the process can no longer allocate) |
| File | `scripts/kernel_assist/memory_guard.py:237` (`lock_memory`), `:326` (`close`) |
| Affects v19 | no (research subsystem), but it is a shipped module |
| Regression | long-standing, not a recent change |
| Safe to fix | yes, fixed here |

**What.** `MemoryGuard.lock_memory()` calls `mlockall(MCL_FUTURE)`, which is
**process-wide**, not scoped to the guard. `close()` undoes it — but
`close()` early-returns when `self._closed` is already set:

```python
def close(self) -> None:
    if self._closed:
        return          # <-- never reaches unlock_memory()
```

`KernelAssistedExecutor.execute_with_monitoring()` reuses one guard across
calls (`with self._memory_guard as mg:`). The first call closes the guard;
the second call's `lock_memory()` then locks the process, and the second
`close()` refuses to unlock it.

**Why it is a problem.** `MCL_FUTURE` makes *every future page fault*
require locked memory, capped by `RLIMIT_MEMLOCK` (8 MB here). After the
leak, any allocation past that budget fails: Python raises `MemoryError`,
and C/C++ allocators that do not check for null **segfault**. Reproduced
directly:

```
5 monitored calls done
allocated 128MB: MemoryError
```

The visible symptom in the test suite was a `z3` segfault inside
`Z3_set_error_handler` (z3's C++ allocator returning null), which aborted
the whole pytest process.

**Fix.** `lock_memory()` refuses to lock on a closed guard, and `close()`
always attempts `unlock_memory()` — including on the early-return path.

**Verification.** `bench_kernel_assist.py` + `bench_redteam.py` together went
from *2 failures + a native crash* to **15 passed**; a 128 MB allocation
after 5 monitored calls now succeeds.

## 4. Medium-Severity Issues

### 4.1 `section_split.py` is not wired into any build — STILL OPEN (documented) — **RESOLVED 2026-10-19**

`obfuscator/section_split.py` is a complete, unit-tested sealed-section
streaming module with **zero non-test references** — `grep -rln section_split`
returns only `tests/test_section_split.py` and `tests/test_section_ro.py`
(plus the two docs below). No build, pipeline or loader path calls it.

This was a *documentation* problem, because `THREAT_MODEL.md` presented
"per-section fresh `os.urandom(16)` nonce" as an active control and marked
the row `TESTED`, and `SECURITY.md` cited it as an example of per-build key
generation. Both now say explicitly that the module is library-only and that
no shipped artifact is section-split, and the module docstring carries a
`NOT WIRED INTO THE BUILD` warning. **The underlying gap (no section-split
loader path, no `--no-section-split` switch) is still open** and needs a
decision: wire it, or drop the module.

> **RESOLVED 2026-10-19** (`docs/AUDIT-2026-10-19-followup.md` §4): the
> module was wired into the hybrid loader as an opt-in feature
> (`--section-split` / `--section-count`).  The escape hatch this section
> asked for is the default: the feature is OFF unless the flag is
> passed, so no `--no-section-split` switch is needed.  The module was
> kept (it is the only sealed-section streaming in the tree, so deleting
> it would have lost a real capability) and the "library-only" wording
> in `SECURITY.md` / `THREAT_MODEL.md` was corrected.

### 4.2 `make lint` can never fail — STILL OPEN (deliberate) — **RESOLVED 2026-10-19**

`Makefile:255` is `-pylint … || pyflakes … || true`; the trailing `|| true`
means the target always succeeds, so the CI step

**Not changed here, on purpose.** `pyflakes obfuscator/ native/ scripts/`
currently reports **1428 findings** (almost all unused imports). Dropping

one-line change, and it is a decision the maintainer should make. The
measured number is recorded here so the decision can be made on evidence.

> **RESOLVED 2026-10-19** (`docs/AUDIT-2026-10-19-followup.md` §5): the
> cleanup campaign ran and the gate is now real.  `ruff.toml` enforces
> F401/F402/F541/F601/F602/F811/F821/F841, `make lint` fails on a
> finding, and CI installs ruff from a **pinned** `requirements-dev.txt`
> so the gate is reproducible.  F403/F405 are ignored with the reason
> recorded, and the consequence of ignoring them (undefined names
> hiding behind star imports) is closed at runtime by
> `scripts/lint/check_undefined_globals.py`, which runs as part of
> `make lint`.

## 20. Final v19 Completeness Assessment

**There is no v19.** The product's own version line is `shadow-compiler 2.0.0`

|---|---|

only as correct as its slowest end-to-end check, and there was none.
