# The Artefact Gate: Compile, Import, Exercise

**Date:** 2026-10-30
**Script:** `scripts/transfer/artefact_gate.py`

This implements the recommendation section 6 of the paper makes, and on its
first run it found **nine failures across 63 artefacts** in two new classes.

## What it does

For every corpus module — nine synthetic tasks, eight corpus tasks, six external
tasks — it generates artefacts at several build indices and then:

1. **parses** them (`compile`), catching syntax errors;
2. **imports** them (`exec_module`), which executes module-level code;
3. **exercises** every surviving callable against the task's properties,
   catching failures that only appear when code runs.

It reports the module, the build index and the exception.

## First run

```
artefacts checked: 63
failures: 9
```

| class | example | count |
|---|---|---|
| `_sumprod` undefined | `external/all_equal`, `external/dotproduct` | 5 |
| `_nx_ee5c35` undefined | `external/median_low` | 3 |
| (one more) | — | 1 |

## What these are

`_sumprod` is a private helper in `cpython/statistics.py`. It is imported and
used by the public functions, and after obfuscation the reference survives while
the binding does not — **the same defect class as `hexversion`**, in a module the
earlier fix was not tested against.

That is the point of a gate rather than a fix: the two renamer repairs were
verified against the cases that had been reported, and this input contains more
of the same kind. A pass-level fix without a corpus-level check leaves the
corpus-level failures intact.

## Why the gate belongs in the repository

Five defects were found by accident, in the order the work happened to reach
them. The gate turns that into a fixed check that runs in one command and
reports by module and index. It is the cheapest assurance this project can have
for a tool whose output is executed, and it is the concrete form of the paper's
recommendation.

## Status

**The gate finds failures; they are not all fixed.** `_sumprod` and
`_nx_ee5c35` are open, and they may share a cause with the renamer defect or be
a separate one — the next step is to reduce `_sumprod` to a minimal case, as
`hexversion` was reduced, rather than to guess.

The gate's value so far: it converted "we fixed the renamer defects" into
"the renamer defects are fixed for the inputs we checked", which is a smaller and
truer statement.

## Round 99: one class fixed, one class remains

The `_sumprod` failures are gone. The cause was not the import rename but the
opposite: the renamer rewrites module-level **uses** but not module-level
**bindings**, so an imported name was caught in between. Renaming the alias fixed
`hexversion` and broke the `try/except ImportError` fallback that rebinds the
same name in a different spelling.

**Reserving the imported name** is the only rule consistent for both: neither
the binding nor any use is renamed, and the module runs.

| state | gate failures |
|---|---|
| before round 98 | (no gate) |
| gate's first run | **9** |
| after reserving imports | **3** |

The three that remain are a different class: `_nx_ee5c35` in
`external/median_low`. That name is generated by a pass, not imported, and it is
referenced without being bound — the reverse of the earlier problem.

## What the reserve rule costs

Imported names are no longer obfuscated. For a name like `hexversion` or
`sumprod` that is a loss of obfuscation, and it is the price of consistency given
a renamer that does not rewrite module-level bindings. The alternative — teach
the renamer to rewrite bindings — is a larger change than this session can verify.

Recorded as a deliberate trade rather than an oversight: the artefact runs, and
one class of identifier keeps its name.

## Guards updated

Two guards asserted the previous behaviour and were rewritten. The second now
executes a `try/except ImportError` fallback and checks the value it computes,
which is the property that matters; the old version asserted the absence of a
particular string, which was a proxy for it.

## Round 100: the gate is clean — 63 artefacts, zero failures

The last class was plain imports. `import numbers` binds `numbers`, and the
renamer renamed the binding while the uses kept their spelling (or the reverse),
so `isinstance(x, numbers.Real)` became a reference to an unbound generated
name.

Applying the same reserve rule to `visit_Import` as to `visit_ImportFrom` fixed
it:

```
artefacts checked: 63
failures: 0
```

Every corpus artefact — nine synthetic tasks, eight corpus tasks, six external
tasks, at three build indices — now parses, imports, and survives being
exercised.

## The path to zero

| round | gate failures | cause addressed |
|---|---|---|
| 98 | **9** | gate built; `_sumprod`, `_nx_ee5c35` found |
| 99 | **3** | reserved `from` imports |
| 100 | **0** | reserved plain imports |

Two rules, both forms of the same one: **a name bound by an import keeps its
spelling, and so does every use.** That is the only invariant consistent with a
renamer that rewrites uses but not module-level bindings.

## What zero means, and what it does not

**Means:** the current corpus is not hit by the six defect classes found so far.
Every artefact in it runs.

**Does not mean:** the obfuscator is correct. The corpus is 23 tasks from three
sources, and six defects were found in it. A seventh class almost certainly
exists in code none of these sources contains — a class with `async`, or
generators, or descriptors, or `except*`.

**Does mean something stronger than before:** there is now a command that
answers "does the output run" over a fixed corpus, in about four minutes, and it
returns zero. Any future transform change can be checked against it.
